## 2. Executive Summary

The interval since the September 12 baseline is **30 non-merge commits and 155 files**
(`git rev-list --no-merges --count 5e796dc..70df6a5`), and it retired the two findings that dominated
the previous pass. **H-5 is fixed the way the last audit asked for it** — `ValidateTradingLimits` moved
from the endpoint into `OrderService.CreateLockedAndConfirmedOrderAsync`, the one place every order is
created, so sub-minimum quote fills are now refused on the path customers actually use. **H-7 is closed
twice over** — `.gcloud-auth/` is gone from the working tree and `.gitignore` carries the pattern.
**M-1 is fixed too**: refusals now travel with their own sentence instead of «خطا در ایجاد سفارش»
(#277, #278, #284, #289).

This run also did the thing the last two audits named and could not do: it **executed the
Production code path.** With `--no-launch-profile` and `ASPNETCORE_ENVIRONMENT=Production`,
Wallet.Api answers `401` with no key, `401` with a wrong key, `200` with the right one, and
`404` for `/api-docs`. The gate works exactly as designed, and N-4 is now a closed row rather
than an inheritance.

One new finding came out of that same experiment, and it is the one this report most wants read:
**the documented way to run this stack disables authentication entirely, and an exported
`ASPNETCORE_ENVIRONMENT=Production` does not survive it.** `dotnet run` — the four commands in
`AGENT.md` and the house driver in `.claude/skills/run-tallaegg/` — applies
`Properties/launchSettings.json`, which sets `Development`. Authentication is registered only
`if (builder.Environment.IsProduction())`, so the run that follows the documentation is the run
with no API key, no authorization fallback policy, and Swagger published. Reproduced A/B in the
same session: `Hosting environment: Development` plus an unauthenticated `200` against
`/api/wallet/balances/{id}`, then `Hosting environment: Production` plus `401` the moment the
launch profile is bypassed. It is reported Medium rather than High because the default `Urls`
bind loopback and the sanctioned deployment path (`install-services.ps1`, published `.exe`,
registry `Environment` values) was verified correct — but it is the finding most likely to stop
mattering only by accident.

On the money path the picture is strong and now measured more completely than before.
**LockedBalance reconstructs from the ledger for all 197 ledger-bearing wallets with zero
divergence** — Freeze − Unfreeze − consumed-collateral rows equals the stored lock, exactly, for
every wallet. Zero matched trades lack a `TradeSettlement` row. Settlement is still exactly-once
by primary key, the wallet's four writers still retry under optimistic concurrency, and the
outbox still claims with a lease. 1,158 tests pass, the clean build is 0 warnings, and no
production package is known to carry an advisory (that census is carried over rather than
re-measured — §9).

What remains open is unchanged in kind: the credit ceiling is still validated on the client and
then locked on the server (H-6, carried over **unverified** in this pass), rate limiting still
does not exist (#279), the best-bid/ask read is still unbounded and still logs the whole order
set as indented JSON (#280), and the 101 Failed / 609 Abandoned outbox rows of 2026-09-01 are
still on the developer database awaiting an operator decision (M-4).

**No Critical findings.** H-5 and H-7 are closed, M-1 went with them, and three rows that had
never been verified — the `Production` branch (N-4), the `AsNoTracking` count (H-3) and the
credential store (H-7) — were checked this time. H-6 is carried over **unverified**. Two new
Mediums are reported (M-5, M-6) together with five Lows (L-2 … L-6), none of which is reachable
by a customer in the product as deployed today.

**A sibling v9 audit of the same commit reaches the same shape.** `AUDIT_2026-09b.md`
(2026-09-26, Gemini 3.8 Flash) also found no Critical, also left the credit race open as its one
High (its H-8), and also verified H-5, H-7 and M-1 closed — while scoring the commit 8.0 against
this report's 7.6. It did not report either of this report's two new Mediums. §4 maps the two
finding-ID spaces and works through where the 0.4 comes from.

### M-6 — A lock that succeeds and a confirmation that fails leave collateral locked on an order nothing will ever release

- **Severity:** Medium · **Confidence:** High (code path read end to end; not executed) ·
  **Effort:** Low · **Already Tracked:** no
- **Location:** `src/Order/Orders.Application/OrderService.cs` — `CreateLockedAndConfirmedOrderAsync`
  (lock at 319-320, confirm at 340, the warning-only branch at 342-343), `ConfirmOrderIfPendingAsync`
  (381-415, whose `catch (Exception)` at 408-414 returns `false` after logging),
  `CreateLockedAndConfirmedOrderForQuoteAsync` (355-359, returns `null` when unconfirmed), and
  `QuoteFillService.AcceptQuoteAsync` (181-187, which cancels the *other* side only); compared
  against `OrderCollateralReconciler.ReleaseResidualLockIfCompletedAsync:52-57`, which returns
  immediately unless `order.Status == OrderStatus.Completed`
- **Evidence:** the lock is taken before the order becomes matchable — the C-5 ordering, which is
  correct — but the failure branch after it only writes a warning: `if (!confirmSuccess)
  _logger.LogWarning("Order {OrderId} was not confirmed.")` and returns
  `(createdOrder, confirmSuccess)`. `ConfirmOrderIfPendingAsync` returns `false` for three different
  reasons and logs all of them the same way: the order is gone, the order is no longer Pending, or
  **an exception was thrown and swallowed** — its `catch` converts a database failure into a `false`
  with no exception, so a transient failure is indistinguishable from a benign race at the call
  site. `QuoteFillService` creates the customer's side first (167-171) and the dealer's second
  (176-179), so *which* order is stranded depends on which side failed: when the dealer's order is
  the one that never confirms, the customer's order is cancelled — releasing the customer's lock —
  and the dealer's order stays Pending with its collateral locked, which is the case this paragraph
  describes; when the customer's order is the one that never confirms, the method returns at 172-173
  before the dealer's side exists and the customer's own lock is stranded instead. Orders runs four
  hosted services — `OutboxProcessorService` (`Orders.Api/Program.cs:188`),
  `AutoQuotePublisherService` (`:252`), `MatchingEngineService` (the loop, registered in
  `MatchingEngineRegistration.cs:39`) and `DatabaseMigrationHostedService` (through
  `AddDatabaseMigrationAtStartup`, `Orders.Api/Program.cs:307`). **None of the four cancels, expires
  or unlocks a Pending order**, so nothing sweeps one, and the reconciler will not touch one because
  it is not Completed.
- **Failure Scenario:** a quote fill for 100 g MAUA creates the customer's order, locks and confirms
  it, then creates the dealer's order, locks 500,000,000 IRT against it, and the confirmation fails
  — say `GetByIdAsync` times out during a SQL Server failover. The customer is told the fill failed
  and their own lock is released; the dealer's 500,000,000 IRT stays in `LockedBalance` behind a
  Pending order that will never be Confirmed, never match, and never be released automatically. The
  same shape occurs on `POST /api/orders`: the caller receives a Pending order and the customer's
  money is locked, which the bot renders as ⏳ indefinitely. The remedy today is manual — an operator
  cancels the order, and `CancelOrderAsync` does release the lock through
  `ComputeResidualLockAsync` — but nothing tells them to, and the stranded amount is invisible in
  every report the bot offers.
- **Recommendation:** make the failure branch release what it locked — call the wallet's unlock for
  `(collateralAsset, collateralAmount)` when `confirmSuccess` is false, or mark the order `Failed`
  and release, in the same way the lock-failure branch already marks it `Failed` at 330-331 (that
  branch releases nothing because nothing was locked). Optionally add a sweeper for Pending orders
  older than a few minutes that releases and cancels them. What exists today, so the change is not
  made blind: the warning log; the manual cancel path, which does release; and the reconciler, which
  is scoped to Completed orders and must stay that way or it would release the collateral of an
  order that is still filling. Confidence is High on the code path and Medium on frequency — no
  instance of this was observed on the developer database, where all 135 orders are
  Completed/Failed/Cancelled and no order is Pending.

## 8. Key Positive Findings

- **The Production request path works, and this audit watched it work.** With `--no-launch-profile`
  and `ASPNETCORE_ENVIRONMENT=Production`, `GET /version` answers `401` with no key and with a wrong
  key, `200` with the right one, and `/api-docs` answers `404` — the Swagger surface really is absent
  in Production, the API-key scheme really is registered, and the global fallback policy really does
  require an authenticated user. Three audits have now said this had never been executed (#105, N-4
  twice); it has been.
- **The lock is now as auditable as the balance.** The previous audit verified that
  `Wallets.Balance` equals the ledger tail for all 45 ledger-bearing wallets. This one adds the other
  half: for all **197** wallets with transactions, `Freeze − Unfreeze − consumed collateral rows`
  equals `LockedBalance` exactly, with **zero** mismatches. The two non-zero locks in the database are
  both on the market maker's account and both fully explained by the ledger, which is what makes the
  residue in §10 a bookkeeping question rather than a silent leak.
- **Every matched trade is settled.** `Trades LEFT JOIN TradeSettlements WHERE s.TradeId IS NULL` →
  **0** rows. The transactional outbox does what it claims: a match and its settlement intent commit
  together, and the intent eventually executes.
- **Exactly-once settlement is still a database guarantee.** `TradeSettlements` is keyed on `TradeId`,
  the insert carries the four balance changes in one `SaveChanges`, and a duplicate answers "already
  settled" rather than moving anything (`WalletRepository.SettleTradeAsync`).
- **The wallet's four writers share one retry.** `WithConcurrencyRetryAsync` re-reads with
  `ChangeTracker.Clear()` between attempts and rebuilds the transaction row, so the recorded balance
  chain is never written from a stale read — the trap that produced #74 in Orders.
- **The outbox claim is a real lease.** `ClaimDueMessagesAsync` selects candidates, claims them with a
  single `ExecuteUpdateAsync` whose conditions are in the `WHERE`, and returns only rows it won, so
  two processors cannot dispatch the same settlement; `MarkAttemptFailed` clears the lease so the
  backoff — not the lease — decides when the retry runs.
- **The bot resolves identity from the chat, not from the request.** Every customer command reads the
  user from `telegramId`; operator commands run only behind `IsOperator(user)` checked against the
  role the Users service reports (`BotHandler.cs:209-214`), and admin screens are gated the same way
  (`IsOperatorAsync`, 729-742, 942-962, 1495-1499). No command lets a customer name another account.
  That is the boundary that actually protects customer money, and it holds.
- **Three things that look like defects were checked against the code that runs, not the comment that
  describes it:** the commented-out price check in `ExecuteAtomicMatchAsync` step 3,
  `IsAllowedCounterparty`'s rule 2, and `ProcessOrderForMatchingAsync`'s break condition. Two of the
  three are covered elsewhere (`FindBestMatch` and `GetMatchingOrdersAsync` both enforce price
  compatibility), and the third is L-2 — reported as a documentation gap rather than a defect, which
  is what the evidence supports.
- **The interval's own discipline shows.** The `.gitignore` entry for `SendExceptions*.txt` was
  removed in the same commit range that deleted its only writer, so a naive diff read of the file
  would report a security regression where there is a cleanup.

## 9. Security Assessment

**Reproduced in this pass:** the authentication boundary in both directions — absent in Development,
present in Production — and the fact that the documented run command lands in the first case whatever
the operator exports (M-5).

**Read, not executed:** `ApiKeyAuthenticationHandler` compares the header with `!=` rather than a
constant-time comparison, and answers `Fail("Invalid API Key")` versus `Fail("Missing API Key")`,
telling a caller which of the two it got wrong. Both are theoretical here: the key is one shared
secret between services on one machine, the comparison runs over a network round trip where timing
noise dwarfs a byte-wise difference, and knowing a key is *missing* rather than *wrong* does not help
anyone who cannot guess either. Recorded so the next reader does not have to re-derive it; not a
finding.

**Still absent, already filed:** rate limiting anywhere in the tree (`AddRateLimiter`,
`UseRateLimiting` — no occurrences; #279). It is bounded today by loopback and stops being bounded
with the web client, which `DIRECTION.md` sequences after the pilot contracts. The single static key
with no rotation story is the same shape of debt: fine for one machine, and a decision owed before a
second consumer exists.

**Secrets:** `config/appsettings.global.json` is untracked and `git status --untracked-files=all` is
empty, so no working-tree secret is staged. `APIKeyConstant` reads `TALLAEGG_API_KEY` from the
environment and throws in Production when it is unset. The installer writes the key into the
service's registry `Environment` value — the standard way to give a Windows service an environment
variable, readable by a local administrator and by the service's own account, which is the posture
this deployment has chosen. `.gcloud-auth/` is gone and gitignored (H-7).

**Package advisories:** the prior audit's census stands unrefuted — all production projects clean,
one transitive High in the test project only (`SQLitePCLRaw.lib.e_sqlite3 2.1.10`,
GHSA-2m69-gcr7-jv3q). This pass did **not** re-run the scan: `dotnet list package --vulnerable
--include-transitive` exceeded the command window this session is given (30 s), so that row is
carried over, not re-measured, and it is named in §15.

**No false certification:** within the scope of §3, no way was found for a customer to move money
they do not have, to reach another customer's account, or to reach a service without a credential in
a correctly deployed Production environment. That is a statement about what was looked at, not a
guarantee.

## 10. Financial & Data Integrity Assessment

**Live-database measurements (read-only `sqlcmd` against the developer's three databases; the queries
are kept in `.audit-work/s2-queries.sql` and `.audit-work/s2-locks.sql`):**

| Measurement | Result |
|---|---|
| Orders | 135 — 132 Completed, 2 Failed, 1 Cancelled, **0 Pending/Confirmed** |
| Trades | 66 |
| Outbox messages | 10,256 — 9,546 Completed, 101 Failed, 609 Abandoned |
| Trades with no `TradeSettlement` | **0** |
| Wallets / Transactions / TradeSettlements | 217 / 14,456 / 9,546 |
| Negative balances | 5 wallets, enumerated below — all consistent with decisions 003/004 |
| Non-zero `LockedBalance` | 2 wallets, both the market maker's |
| `LockedBalance` reconstruction, all 197 ledger-bearing wallets | **0 mismatches** |
| `Users` indexes | PK_Users, IX_Users_TelegramId (unique), IX_Users_PhoneNumber (unique, filtered) |
| Duplicate phone numbers | **0** groups |

**One apparent contradiction in that table, resolved before it misleads anyone:** 66 `Trades` but
9,546 `TradeSettlements` rows. The two numbers measure different things because the simulator deletes
a run's trades and keeps what their settlement left behind — the same reason 10,190 of the 10,256
outbox messages reference an aggregate id that no longer exists. Both figures are therefore
*residue-bearing counts*, not live business volumes, which is exactly what `AGENT.md` warns about when
it says a count from those tables proves nothing. The row that does mean something is the next one:
of the trades that do exist, none is unsettled.

**The ledger explains the lock, not just the balance.** Freeze − Unfreeze − the `Trade` rows whose
`BallanceBefore` equals `BallanceAfter` (the consumed-collateral legs, which by design leave `Balance`
untouched) equals the stored `LockedBalance` for every wallet with transactions — 197 of them, zero
divergence. The same expression reproduces both non-zero locks to the toman and to the gram.

**Two locks have no order behind them, and they are permanent.** The market maker's wallet holds
**1,014,238,920 IRT** and **95.01 g MAUA** locked while the Orders database contains no open order at
all — all 135 are Completed, Failed or Cancelled. Both are ledger-consistent, so they are collateral
that was really reserved and never released, not a bookkeeping artefact. Placed in time: the MAUA
wallet's last lock was recorded 2026-09-01 15:10 and the IRT wallet's last movement was the unlock of a
cancelled order on 2026-09-08 17:53. The two commits that close this class of loss both landed after
the fact — `154ac52` (#185, "settle before resetting") and `fa89b85` (#257, delete both sides of a
fill, whose own comment names the stranding of a real wallet's `LockedBalance` as the thing its guard
exists to prevent). So this is **residue from simulator runs that predate the guards, and it is
permanent**: nothing sweeps it, and no order survives to reconcile against. Production never runs the
simulator, so no deployed environment can contain it. `AGENT.md` documents the orphan-*trade* half of
this residue and says a count from those tables proves nothing; it does not mention the
orphan-*lock* half, which is what the two figures above are. Recommended: a one-off reconciliation on
whichever developer machines show a non-zero lock with no open order, and a sentence in `AGENT.md`
next to the orphan-trade note. Not a live defect, and not given a finding ID for that reason.

**The 101 Failed / 609 Abandoned settlements are unchanged since 2026-09-01.** All 101 sit inside a
four-minute nineteen-second window (09:15:50–09:20:09 on 2026-09-01) and their settlement payloads
reference trades that no longer exist — 10,190 of the 10,256 messages do, because the simulator
deleted those trades. The machinery to resolve them exists (`/api/outbox/unsettled`, `/redrive`,
`/abandon`, the "SETTLEMENT STUCK" alert); what is missing is the operator decision, which is exactly
what M-4 records. Because those messages are `Failed`/`Abandoned` and cannot be silently revived, they
are inert — but they also mean an `OutboxMessages` count is not a measure of anything, which `AGENT.md`
already says.

**Market maker exposure.** −1,311.58 MAUA on the shop's own account, with the toman side positive. Per
[decision 003](../decisions/003-market-maker-balance-is-the-shops-book.md) that is the book, not an
overdraft, and it must not be reported as a data-integrity problem. What is genuinely missing is
unchanged: no alerting on the size of the exposure (#124).

**Credit.** The five negative balances, enumerated rather than sampled — a joined read of each
negative row against the same user's `CREDIT_` rows, not an assumption:

| Negative wallet | Balance | Covered by (same user) |
|---|---|---|
| MAUA | −1,311.58000000 | `CREDIT_MAUA` 0.00000000 — the market maker's own book (decision 003) |
| IRT | −318,279,626.00000000 | `CREDIT_SEKE_BAHAR` 10 (≈980M IRT at the 2026-09-10 quote of 97.9M/coin) |
| MAUA | −17.26000000 | `CREDIT_MAUA` 40.00000000 |
| BTC | −1.11011000 | `CREDIT_BTC` 10.00000000 |
| MAUA | −1.11000000 | `CREDIT_MAUA` 50.00000000 |

Four of the five are covered within their own asset; the toman debt is covered by the **coin** ledger,
which is the cross-asset rule of [decision 004](../decisions/004-credit-is-cross-asset.md) doing its
job rather than a hole. There is no `CREDIT_IRT` row for that user, and that is also decision 004:
credit ledgers are minted per tradable **base** asset, so `CREDIT_IRT` is not a currency and half of
the cross-asset design is unreachable rather than absent. Whether it should exist is #36's question,
not a new finding. The market maker's own negative row is the last of the five and is not customer
debt at all.

performed in this pass; the money-path statements above are measurements of stored state, which is what
the methodology asks a session-2 pass to produce.

## 11. Architecture Assessment

- **The deployed architecture matches its documentation**, and the documentation is unusually
  specific: three small services plus a bot, no matching service (it is a library inside Orders), a
  leader lease so two instances agree on who sweeps, a readiness gate that answers 503 until the
  migration has applied, and an inert `TallaEgg.Api` that registers a `DbContext` and maps nothing.
  `install-services.ps1` installs four Windows services and deliberately not the other two, with the
  reason written at the top of the file. Nothing here contradicts itself.
- **The patterns are load-bearing, not ornament.** Outbox with lease claiming (#160), the leader lease
  for the sweep, `WithConcurrencyRetryAsync` with `ChangeTracker.Clear()`, the Pending-before-lock
  ordering (C-5), the `(WalletId, ReferenceId)` unique index, the filtered unique index over
  `Users.PhoneNumber` — each one answers a named incident, and each one was found in this pass doing
  the job its comment claims.
- **The weakest structural point is lifecycle, not layering.** `Pending` is a state an order enters and
  leaves only through a human: nothing expires it, nothing sweeps it, and the reconciler is scoped to
  `Completed`. That is what makes M-6 possible, and it is the same gap from the other side as the
  missing alerting on maker exposure (#124) and on stuck settlements (M-4): the machinery that notices
  an anomaly is thinner than the machinery that prevents one.
- **Unbounded reads remain** (#280): `GetOrdersByAssetAsync` takes every historical order for a symbol
  into memory, and `OrderService.GetBestBidAskAsync` logs that set whole. It is the documented M-3 and
  the reason the best-price path is measured in rows rather than milliseconds.
- **The dual ledger is still a trap for the next reader**: `WalletTransactions` is written by nothing,
  read by a live endpoint that always answers empty, and described truthfully in that endpoint's own
  description (L-5).
- **Two dependency-hygiene items, both Low and both cheap.** `Orders.Application` references the
  Telegram bot project that its compiled output does not use, so `Orders.Api` deploys 3.4 MB of bot
  assemblies including `Telegram.Bot` (L-3); and the shared `UsersApiClient` declares the namespace
  `TallaEgg.TelegramBot.Infrastructure.Clients` while living in `TallaEgg.Infrastructure` — which is
  precisely why that unused reference reads as necessary. Neither changes behaviour; both mislead a
  reader who trusts them.
- **The bot is still a 1,700-line partial class** doing dispatch, flows and message building. It has
  never been the source of a money bug — the server owns the money rules — and
  `BotConversationFlowTests` plus the message tests pin most of its behaviour. Not a finding, and still
  the likeliest future maintenance cost.
