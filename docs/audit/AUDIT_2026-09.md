## 2. Executive Summary

The codebase remains in materially better shape than its score history suggests, and the
hardening work since the August pass is visible in nearly every money path: settlement is
exactly-once by database constraint, wallet writes retry under optimistic concurrency,
deposit idempotency (#157) landed and was verified working, and outbox delivery is
lease-claimed and batch-resilient. On a read of the live developer database, 14,034
transaction rows reconstruct every one of 45 ledger-bearing wallet balances with zero
divergence, and the credit-backed negative positions all check out against the documented
cross-asset model.

Two reproduced findings nonetheless sit on the live trading path, and both are about the
same structural fact: **the credit ceiling is enforced by a client-side composition of
four HTTP balance reads followed by a lock that deliberately enforces nothing.** That
composition (a) never applies the symbol trading limits on the quote-fill path — the only
path customers actually trade on — and (b) races: two concurrent quote accepts against a
balance sufficient for one were both validated, both locked, both settled, and left a
customer 1,000,000 IRT in debt with zero credit behind it. The first is new; the second is
the concrete, reproduced form of the already-tracked #36.

One hygiene finding sits closest to a leak: an untracked `.gcloud-auth/` directory holding
an SSH **private key** and gcloud credential databases lives inside this public
repository's working tree and is not covered by `.gitignore`.

- **H-5 (High, reproduced):** trading limits (MinQuantity/MinNotional/MaxQuantity) are
  enforced only on the order-book path; the dealer quote path executes below-minimum orders end-to-end.
- **H-6 (High, reproduced):** the validate-then-lock race lets a user exceed their credit
  ceiling; N concurrent orders ≈ N× leverage. Root design issue already tracked as #36.
- **H-7 (High):** untracked cloud credential store with an RSA private key inside the repo
  root, not gitignored — one `git add .` from being published.
- **M-1 (Medium, reproduced):** specific business refusal messages are swallowed into the
  generic «خطا در ایجاد سفارش» before reaching any caller.

No Critical findings are open. The residual picture is unchanged in kind from August:
strong mechanisms, thin operational surfaces (no rate limiting, no alerting on maker
exposure (#124), debt visibility (#61)), and a Production-mode branch of every service that
this audit — like the one before it — still never executed.

## 6. High-Priority Findings

### H-5 — Trading limits are not enforced on the quote-fill path, the only path customers trade on

- **Severity:** High · **Confidence:** High · **Effort:** Low · **Already Tracked:** no
- **Location:** `src/Order/Orders.Application/Services/QuoteFillService.cs` (`AcceptQuoteAsync`,
  whole method); `src/Order/Orders.Application/OrderService.cs:233` (`ValidateTradingLimits` —
  called only from `CreateOrderAsync(OrderDto)`, line 98)
- **Evidence:** `ValidateTradingLimits` — the sole reader of the configured
  `MinQuantity`/`MaxQuantity`/`MinNotional` pair limits — is invoked only in
  `OrderService.CreateOrderAsync(OrderDto)`. `QuoteFillService.AcceptQuoteAsync` rounds the
  quantity, checks `> 0`, dealer mode, quote existence and balance/credit, then creates and
  matches both orders. The bot enforces no minimums either (grep: no `MinQuantity`/`MinNotional`
  in `TelegramBot/`). Every symbol currently runs in Dealer mode
  (`Matching:RequireMarketMakerCounterparty=true`), so the enforcing path is the one nobody
  reaches. The limits' own doc comment states the stake: *"Configured limits that are never
  applied are worse than none."*
- **Failure Scenario:** a customer accepts a published quote for 0.05 g MAUA
  (MinQuantity is 0.1 g): the trade executes and settles, though the order path refuses the
  identical order. Sub-MinNotional dust trades and above-MaxQuantity orders are equally
  possible — the latter still bounded by the balance/credit check, so the practical damage is
  rule inconsistency and dust economics, not unlimited exposure.
- **Reproduction:** disposable DBs + locally running services. `POST /api/quotes/accept`
  `{userId: customer, symbol: "MAUA/IRT", side: 0, quantity: 0.05}` against a quote of
  9,900,000/10,000,000 → HTTP 200 `{"success":true,"message":"معامله با موفقیت انجام شد.",…}`;
  after the outbox drained, the customer's wallet showed IRT 0 / MAUA 0.05. Control: the same
  size on `POST /api/orders` is refused.
- **Analysis/Risk:** a control the team added believing it protects the shop is silently
  absent on the path every customer uses; operators tuning `Symbols` limits in config get no
  protection and no error.
- **Recommendation:** call `ValidateTradingLimits` (or the shared pair-info check) in
  `AcceptQuoteAsync` before the balance check, and add a quote-path case to `TradingLimitTests`.

### H-6 — The credit ceiling is enforced by an un-atomic read-then-lock, so concurrent orders exceed it (root of #36)

- **Severity:** High · **Confidence:** High · **Effort:** Medium · **Already Tracked:** #36
  (same root: ceiling enforced at order time only); the concurrent-exploit shape is new
- **Location:** `src/TallaEgg/TallaEgg.Infrastructure/Clients/WalletApiClient.cs:241`
  (`ValidateCreditAndBalanceAsync` — four sequential balance reads composed client-side);
  `src/Wallet/Wallet.Core/Wallet.cs:109` (`LockBalance` deliberately enforces nothing —
  Section 0); `src/Order/Orders.Application/Services/QuoteFillService.cs:131-153` (check, then
  create-and-lock)
- **Evidence:** the ceiling lives in `CREDIT_<ASSET>` rows, so per Section 0 the check
  belongs where all rows are visible — today that is a *client* that reads four balances over
  HTTP and then asks `Wallet.Api` to lock. `LockBalance` enforces no sufficiency rule by
  design, so whatever happens between read and lock is not prevented, it is consumed.
- **Failure Scenario:** a customer with 1,000,000 IRT and no credit places two 1,000,000 IRT
  buys at once. Both validations read the same balance before either lock lands; both locks
  succeed (they enforce nothing); both trades settle. The customer holds 0.2 g of gold and a
  1,000,000 IRT debt with zero credit — uncollateralized exposure to the shop. N concurrent
  orders ≈ N× leverage.
- **Reproduction:** disposable DBs + locally running services. Customer funded to exactly
  1,000,000 IRT (balance re-read confirmed `{"balance":1000000,"lockedBalance":0}`). Two
  concurrent `POST /api/quotes/accept` (quantity 0.1 @ 10,000,000) → **both** returned success
  (trades `93e98b06…`, `d6b898e2…`); outbox settled both (`OutboxMessages`: 3/3 Completed);
  final wallet: **IRT −1,000,000.00, CREDIT_MAUA 0.00000000, MAUA 0.25**.
- **Analysis/Risk:** bot customers cannot easily race (Telegram updates are processed
  sequentially per polling loop), so today's exploit path is direct API access, an insider,
  or — critically — the planned web client (#97, labelled `security`), which would put this
  one browser click away from every user. This is a reproduced, money-moving gap, not a
  hypothetical; it is reported High rather than Critical solely because no
  customer-reachable concurrent path exists in the product as shipped today.
- **Recommendation:** make validation and locking one Wallet-side operation: an endpoint
  that reads balance + both credit rows, applies the ceiling, and locks in a single
  transaction on the wallet database (the same home `SettleTradeAsync` already has). #36's
  single-signed-ledger redesign subsumes it; until then, at minimum apply the check inside
  the lock path server-side. Add the concurrent-accepts case to the test suite.

### H-7 — Untracked cloud credential store with an RSA private key sits inside the repository working tree

- **Severity:** High · **Confidence:** High (facts verified; nothing has leaked yet) ·
  **Effort:** Low · **Already Tracked:** no
- **Location:** repository root, `.gcloud-auth/` (untracked). Shape recorded, contents not
  copied (redaction rule): `google_compute_engine` (1,675 bytes, `-----BEGIN RSA PRIVATE
  KEY-----`), `google_compute_engine.ppk`, `credentials.db`, `access_tokens.db`,
  `default_configs.db`, `legacy_credentials/`.
- **Evidence:** `ls -la .gcloud-auth/` (listing above); `grep gcloud .gitignore` → **no
  match** (exit 1); `git status` shows `.gcloud-auth/` untracked alongside
  `bootstrap-ssh-temporary.ps1` and `scripts/aws-pasarguard-userdata.sh`.
- **Failure Scenario:** any command that stages the working tree (`git add .`, the
  repository's own house-cleaning PowerShell, a future agent run instructed to "commit
  everything") publishes the shop's cloud credentials to a public repository — the exact
  class of incident #33 spent its rotation cycle cleaning up.
- **Reproduction:** not applicable (state observation, not behavior). The listed commands and
  their outputs are in `.audit-work/04-synthesis.md` and §8.
- **Analysis/Risk:** this repository's public history already contains rotated credentials
  and a documented policy about them; a live private key one staging step away from `main`
  deserves the same discipline before it needs a second rotation.
- **Recommendation:** move `.gcloud-auth/` out of the repository directory entirely, and add
  `.gcloud-auth/` (plus the other two untracked files or a broader local-artifacts pattern)
  to `.gitignore` as belt-and-braces. Consider the SSH key compromised by proximity and
  rotate it if it guards anything real.

## 10. Architecture Assessment

- **The deployed architecture is three small services plus a bot**, matching the
  documentation: no Matching service (library inside Orders), an inert bot port, a dormant
  Affiliate stack (out of scope), and `TallaEgg.Api` mapping nothing. What the docs claim
  about the topology checks out.
- **Patterns are load-bearing, not ornamental:** the transactional outbox with lease-based
  multi-instance claiming (#160), a leader lease for the matching sweep, a database
  readiness gate with 503s (#230), config flattening with correct provider precedence
  (#159/#181), and a version endpoint (#218). Each exists because a named incident demanded
  it, and the commit log since the last audit keeps paying those debts down.
- **Weak points:** the dual transaction ledgers (legacy `WalletTransactions` still has a
  live endpoint that always answers empty — documented, but a trap for the next reader);
  `GetOrdersByAssetAsync` fetches every historical order for an asset and filters in memory
  (unbounded, feeds both the matching loop and best-price — **M-3**); the commented-out
  price check inside `ExecuteAtomicMatchAsync` step 3 is dead weight now that
  `FindBestMatch`/`GetMatchingOrdersAsync` enforce compatibility; and
  `ProcessOrderForMatchingAsync`'s break condition works only through EF identity resolution
  sharing one context — currently correct, fragile to a future refactor.
