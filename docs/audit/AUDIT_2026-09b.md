## 2. Executive Summary

This audit evaluates release commit `70df6a5c` (version 1.6.0 candidate) of the **TallaEgg** platform, an automated gold and currency trading microservice platform running under .NET 9 with a Telegram Bot front-end.

Since the baseline audit on September 12, 2026 (`AUDIT_2026-09.md` at commit `5e796dc6`), **29 non-merge commits** have landed, addressing critical operational risks:
1. **Remediation of High Severity Finding H-7:** The untracked `.gcloud-auth` directory containing private SSH/RSA keys was eliminated and placed in `.gitignore` (commit `b812034`).
2. **Remediation of High Severity Finding H-5 & Medium Finding M-1:** Centralized order limit enforcement (`MinQuantity`, `MaxQuantity`, `MinNotional`) was added directly into `CreateLockedAndConfirmedOrderAsync` (commit `fc6016e`), ensuring trading bounds cannot be bypassed via Quote Acceptance endpoints, and informative business refusal messages are surfaced directly rather than obscured under generic error strings.
3. **Critical Multi-Account Contact Card Injection Fix (#303):** Strict verification was implemented ensuring Telegram contact cards match the sender (`Contact.UserId == senderId`), and phone ambiguity handling was enforced across administrative commands.
4. **Resilient Wallet Client Outage Handling (#290):** The system now clearly discriminates between an uncreated wallet (0 balance) and a temporary wallet service outage (`BalanceRead.Unavailable`), preventing transient connectivity errors from falsely reporting to users that their funds are exhausted.

## 6. High-Priority Findings

### H-8 — Un-atomic Credit Verification and Balance Locking on Multi-Threaded Order Entry (Residual of #36)

- **Severity:** High
- **Confidence:** High
- **Estimated Effort:** Medium
- **Already Tracked:** GitHub Issue #36
- **Location:** `src/TallaEgg/TallaEgg.Infrastructure/Clients/WalletApiClient.cs:250` (`ValidateCreditAndBalanceAsync`), `src/Order/Orders.Application/Services/QuoteFillService.cs:135` (`AcceptQuoteAsync`), and `src/Wallet/Wallet.Core/Wallet.cs:109` (`LockBalance`).
- **Evidence:** Credit validity is evaluated across multiple HTTP balance queries in `WalletApiClient.ValidateCreditAndBalanceAsync`. `Wallet.LockBalance` intentionally does not validate sufficiency because it only possesses visibility over a single asset row (per Decision 005 and Section 0).
- **Failure Scenario:** A client submitting two concurrent requests via an external API client on the same user account with insufficient collateral can exploit the time window between the balance read and the balance lock, causing both operations to lock funds and commit a position beyond the user's authorized credit ceiling.
- **Reproduction:** As established in baseline reproduction REPRO-2, two simultaneous requests to `/api/quotes/accept` with marginal collateral both succeed before locking occurs. Currently contained on Telegram bot front-ends due to per-chat sequential update processing, but poses a direct financial risk if public Web APIs (#97) are exposed without server-side atomic locking.
- **Analysis & Risk:** While cross-asset credit validation is structurally necessary, executing it across multiple HTTP roundtrips leaves a concurrency window.
- **Recommendation:** Implement an atomic stored procedure or single database transaction endpoint (`LockBalanceWithCreditCheck`) within `Wallet.Api` that evaluates both the primary balance and corresponding `CREDIT_<ASSET>` rows inside a single database transaction.

## 7. Medium and Low Findings

### M-5 — Lack of Application-Level Rate Limiting on Service Endpoints

- **Severity:** Medium
- **Confidence:** High
- **Estimated Effort:** Low
- **Already Tracked:** GitHub Issue #279
- **Location:** `src/Order/Orders.Api/Program.cs`, `src/Wallet/Wallet.Api/Program.cs`, and `src/User/Users.Api/Program.cs`.
- **Evidence:** Full-text codebase search reveals no usage of `Microsoft.AspNetCore.RateLimiting` middleware.
- **Analysis & Risk:** Under the current deployment topology, APIs are bound to loopback (`127.0.0.1`) and consumed solely by the Telegram Bot process. However, during the rollout of the web interface (Issue #97), the absence of rate limiting will expose the system to denial-of-service and credential brute-force attacks.
- **Recommendation:** Register `AddRateLimiter` in all API entrypoints with partition keys based on client IP / User ID.

### M-6 — In-Memory Order Book Filtering and Excessive Serialization in `best-prices`

- **Severity:** Medium
- **Confidence:** High
- **Estimated Effort:** Low
- **Already Tracked:** GitHub Issue #280
- **Location:** `src/Order/Orders.Application/Services/QuoteFillService.cs` / `GetBestBidAskAsync`.
- **Evidence:** The query retrieves historical orders matching an asset and filters active records in memory rather than pushing predicate filters down to SQL Server.
- **Analysis & Risk:** As the `Orders` table grows beyond hundreds of thousands of rows, response times on price discovery endpoints will degrade significantly.
- **Recommendation:** Push status and timestamp predicates down into the EF Core LINQ query with appropriate database indexes on `(Symbol, Status, CreatedAt)`.

### L-2 — Non-Sargable Column Operation in Asset Lookup

- **Severity:** Low
- **Confidence:** High
- **Estimated Effort:** Low
- **Already Tracked:** GitHub Issue #282
- **Location:** `src/Wallet/Wallet.Infrastructure/WalletRepository.cs:275`.
- **Evidence:** Queries use `w.Asset.ToUpper() == asset.ToUpper()`.
- **Analysis & Risk:** Applying `ToUpper()` directly on the database column prevents SQL Server from performing index seeks, defaulting to an index/table scan. Note: Any modification must preserve case-insensitivity by ensuring input strings are normalized prior to querying, as database column collation must be verified.
- **Recommendation:** Normalize asset parameters to uppercase before query execution and query `w.Asset == normalizedAsset`.
