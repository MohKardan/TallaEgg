## 2. Executive Summary

This audit uncovered two **Critical** vulnerabilities inside the Telegram Bot gateway, which is the system's primary user-facing interface. 
1. **IDOR via Callback Data**: Any user can iterate through GUIDs to view others' active orders and trade history, and crucially, to cancel active orders belonging to other users. 
2. **TOCTOU Balance Limit Bypass**: A race condition in the Telegram Bot's order confirmation flow allows a user to bypass their global credit and balance limits by opening multiple confirmation prompts and approving them simultaneously.

These two critical findings cap the overall security and financial integrity scores significantly. While the underlying microservices (Wallet, Orders, Users) use solid transaction patterns (e.g. EF Core optimistic concurrency retry loops, outbox patterns), their lack of API-level authorization relies entirely on the flawed Telegram Bot.

## 5. Critical Findings

### [C-1] Missing Authorization Checks on Callback Queries (IDOR)
* **Location:** `TallaEgg.TelegramBot.Infrastructure\BotHandler.cs` inside `HandleCallbackQueryAsync`.
* **Description:** The bot processes callback queries for listing orders (`orders_`), listing trades (`trades_`), and canceling orders (`cancel_order_`) without verifying that the user initiating the callback owns the target resources. 
* **Reproduction Scenario:** 
  1. An attacker sends a crafted Telegram callback query with `data = "orders_<victim_uid>_1"`. The bot parses this, ignores the attacker's `telegramId`, and queries `_orderApi.GetUserOrdersAsync(uid)`. The attacker receives the victim's order history, exposing the victim's order GUIDs.
  2. The attacker then sends a callback query with `data = "cancel_order_<victim_order_guid>"`. The `data.StartsWith("cancel_order_")` block extracts the GUID and calls `_orderApi.CancelOrderAsync(orderId)` blindly.
  3. The victim's active order is canceled without their consent.

### [C-2] Time-Of-Check-To-Time-Of-Use (TOCTOU) Balance Limit Bypass
* **Location:** `TallaEgg.TelegramBot.Infrastructure\BotHandler.cs` (`HandleEnterPriceAsync` and `HandleOrderConfirmationAsync`) and `WalletRepository.cs` (`LockBalanceAsync`).
* **Description:** The bot verifies the user's balance (`ValidateCreditAndBalanceAsync`) *before* displaying the order confirmation prompt. However, when the user clicks "Confirm" (`HandleOrderConfirmationAsync`), the bot submits the order directly to `SubmitOrderAsync` without re-verifying the balance. Furthermore, the downstream `LockBalanceAsync` in the Wallet service only deducts the amount without checking if `Balance + Credit >= Amount`.
* **Reproduction Scenario:** 
  1. A user has a total available balance of 100 USD.
  2. The user initiates a buy order for 100 USD. The bot checks the balance, finds it sufficient, and sends the "Confirm / Cancel" inline keyboard. The user does *not* click anything yet.
  3. The user initiates a second identical buy order for 100 USD. The bot again checks the balance (still 100 USD), finds it sufficient, and sends a second "Confirm" keyboard.
  4. The user clicks "Confirm" on *both* messages in quick succession.
  5. Both calls proceed to `SubmitOrderAsync` because there is no secondary balance check. `LockBalanceAsync` executes twice, pushing the user's balance to -100 USD and creating money out of thin air.

## 6. High-Priority Findings

### [H-1] Price Validation Commented Out in ExecuteAtomicMatchAsync
* **Location:** `Orders.Infrastructure\OrderMatchingRepository.cs` (`ExecuteAtomicMatchAsync`).
* **Description:** The price compatibility check `if (currentBuyOrder.Price < currentSellOrder.Price)` inside the atomic transaction is commented out (lines 158-161). The protection relies entirely on the caller (`MatchingEngineService.FindBestMatch`). 
* **Reproduction Scenario:** Since `MatchingEngineService` currently pre-validates prices, this cannot be easily triggered from the Bot interface. However, any new internal service directly calling `ExecuteAtomicMatchAsync` with mismatched orders would cause immediate financial loss.

### [H-2] Missing Authorization on Loopback APIs
* **Location:** All endpoints in `Wallet.Api` and `Orders.Api`.
* **Description:** The internal microservices lack API-level authorization (no JWT or caller validation). They trust any caller that can reach the loopback network. This violates defense-in-depth principles.

## 12. Production/MVP Readiness — fix before release

The system is **NOT** ready for production.
1. Fix the IDOR in `BotHandler.cs` by ensuring `telegramId` matches the owner of the order/wallet being accessed or cancelled.
2. Fix the TOCTOU Balance Bypass by pushing the `Balance + Credit >= Amount` check down into the `WalletEntity` or `WalletRepository.LockBalanceAsync` so it is enforced atomically inside the database transaction.

3. **[H-1]** Uncomment the price compatibility check in `ExecuteAtomicMatchAsync`.
