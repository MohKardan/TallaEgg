## 4. Section 0 — Things That Look Like Defects and Are Not

Every item in AGENT.md's "Business rules that look like bugs" was checked against the code.
None is reported as a defect; each was confirmed to behave as documented:

1. **Market maker may go arbitrarily negative, no ceiling.** Verified end to end: admins bypass
   the pre-trade credit check (`OrderService` and the bot both gate on role), `LockBalance`
   enforces no sufficiency rule, and `Quote`'s doc comment states the no-quantity-cap decision
   explicitly, pointing at #61. The alerting gap remains #124's, not a finding here.
2. **Commission deliberately 0.00.** `CreateTrade` hardcodes 0.000m rates with a comment naming
   the MVP decision and #35. Dormant, not dead.
3. **Credit is cross-asset.** `ValidateCreditAndBalanceAsync` computes both
   `(spotBase + creditBase) + creditQuote/price` and `(spotQuote + creditQuote) + creditBase*price`
   — exactly the documented semantics. A failed balance lookup is treated as zero, which can only
   refuse a trade, never permit one.
4. **`Wallet.LockBalance` enforces no balance rule, and must not.** The commented-out guard is
   gone entirely; the method now documents why the invariant cannot live on a single-asset entity
   and guards only the amount's sign (the N-6 fix).
5. **Dead bot tokens in the repo.** The literal in `TelegramBot.Infrastructure/Program.cs`
   (~line 141) was verified present and is **not reported** — rotated under #33, history
   deliberately kept, per CLAUDE.md.

## 7. Key Positive Findings

Genuine strengths, verified this pass:

1. **The structural guards are real and were executed, not just read.** A second settlement of
   the same trade is refused by the schema (`TradeSettlements.TradeId` is the primary key) and
   surfaces as an idempotent success (§9 R1). A stale wallet writer is refused by the `Version`
   token (§9 R3). These are the two guarantees the whole money path rests on.
2. **Fixes were applied at the invariant, not the call site.** The August audit's main criticism
   — "contained today, re-opened by the next caller" — has been answered for every item it named:
   wallet concurrency token (#143), legacy methods deleted (#145), stub deleted (#144), lock-sign
   guard (#122). The "one definition per quantity" discipline continued: collateral lock, trade
   value, and residual release each have exactly one formula, shared.
3. **Clean build, zero warnings; 501 green tests on every PR** (Release configuration, solution-
   scoped, artifacts uploaded on failure). CI is the only gate left because merges use
   `gh pr merge --admin`; the workflow comments say so out loud.
4. **Failure-path engineering in the outbox**: per-row save isolation (one bad row cannot stall
   a batch), exponential backoff, an operator-visible stuck-settlement list, re-drive and abandon
   endpoints, mandatory abandon reason. Reconciliation tooling most MVPs never build.
5. **Configuration discipline**: one shared file, fail-fast on missing sections, API key from the
   environment with a throwing accessor in Production wiring, dev placeholder clearly labelled.

## 9. Financial & Data Integrity Assessment

**Reproduction evidence** (harness, in-memory SQLite; log in `.audit-work/repro-out.log`):

- **R1 — double settlement refused (guard proven).** Same trade id settled twice: first
  `success=True 'Trade settled.'` (buyer IRT locked 60→0, seller MAUA locked 5→0, buyer MAUA +5
  created, seller IRT +60 created, 1 settlement row, 4 transaction legs); second
  `success=True 'Trade already settled.'` with every balance unchanged, still 1 settlement row.
- **R2 — deposit idempotency gap (defect reproduced).** `IncreaseBalanceAsync` twice with the
  same `ReferenceId`: balance **2,000,000** (not 1,000,000), **2** transaction rows sharing the
  ReferenceId. The `POST /api/wallet/deposit` endpoint calls this method directly and adds no
  dedup (code-verified).
- **R3 — stale writer refused (guard proven).** Two contexts, one wallet: writer A commits
  (100→150, Version 0→1); writer B, on the stale read, gets `DbUpdateConcurrencyException`;
  final state 150 / Version 1.

### New finding

**F1 (Medium, reproduced): deposit/withdrawal have no idempotency key.** `ReferenceId` is stored
and indexed on `Transaction` but never checked for prior use. The bot issues single `PostAsync`
calls with no automatic retry (verified), so the realistic trigger is a lost response (timeout
after server commit) followed by a human re-send of the admin charge command. Impact: a
customer's IRT or `CREDIT_` balance credited twice; the audit trail shows two rows sharing one
reference — detectable, but only if someone looks. Remedies that fit the existing design: a
unique index on `(UserId, Asset, ReferenceId)` for deposit/withdrawal types with
treat-duplicate-as-success semantics (mirroring `TradeSettlements`), or an explicit idempotency
key at the endpoint. Not High because the actor is the shop's own admin, the window is
human-scale, and the payer sees the resulting balance immediately afterwards.

Everything else on the money path checks out: settlement atomicity and idempotency (R1), wallet
concurrency (R3), uniform decimal(28,8) precision across all money columns, lock-ceiling /
consume-floor rounding direction guaranteeing consumption ≤ lock, withdrawals unable to overdraw,
and credit-backed settlement deliberately bypassing the non-negative guard via
`ConsumeLockedBalance` (correct, and documented). The order-time-only credit ceiling remains a
validate-then-act pair (TOCTOU), bounded today by the bot's sequential update handling; the model
refactor that removes the gap is #36.

## 10. Architecture Assessment

Clean Architecture layering holds per service with a shared `TallaEgg.Core`; AGENT.md's
architectural claims were each verified (no Matching service — it is a library inside Orders;
`TallaEgg.Api` maps no endpoints; the runnable bot project is
`TallaEgg.TelegramBot.Infrastructure`). The transactional outbox keeps cross-service settlement
reliable without distributed transactions, and the dealer-mode quote model removes
resting-liquidity collateral entirely.

Observations worth carrying (none rise above Low):

- Two `Get*OrdersWithLockAsync` methods take no lock at all — the optimistic concurrency token
  is the actual guard (deliberate, provider-independent, documented in `OrderConfigurations`);
  the names overstate the mechanism.
- The price-compatibility check inside `ExecuteAtomicMatchAsync` is commented out. Every current
  caller enforces buy ≥ sell (`FindBestMatch`, quote-fill same-price sides), so no live path can
  match a crossed book — but the repository layer itself would accept one.
- The shared config file is registered *after* the default providers, so it overrides environment
  variables and command line — deployment knobs (connection strings, ports) cannot vary per host
  without editing the file. Relevant to #105's checklist.
- `AutoQuotePublisherService` publishes whatever the first reference-price provider returns; only
  ≤0 and inverted spreads are rejected. A glitched source (unit slip, stale cache) becomes a
  customer-tradeable price within one 2-minute tick. A per-symbol plausibility band or a
  max-move-per-tick clamp would close it cheaply. (Reasoned, not reproduced — §14.)
- Cosmetic: dead request records at the bottom of `Wallet.Api/Program.cs`; the `Wallet.Tests`
  directory shell (bin/obj only); `C:\Users\shahi\...` content links in two csproj files;
  comments still describing the Order price column as (18,2) after the (28,8) widening.
  *(Extended 2026-08-29 review pass: two more stale-precision sites found and verified —
  `QuoteConfiguration.cs:16–20` and `CurrenciesConstant.cs:287–289`, both claiming Orders.Price
  is decimal(18,2) since before #146 widened it; see the §9 correction.)*

## 11. Production/MVP Readiness — fix before release

**Production readiness: ~65%** (was ~55%). The percentage is dominated by one fact that no code
change since August has altered: the Production configuration of every service has never been
booted.

Fix before release, in this order:

1. **Boot the full stack in Production mode once, deliberately** (#105, prior N-4). This is the
   first-ever execution of the API-key path, the CORS whitelist, the Windows-service hosting and
   every `Require*()` configuration guard. Until it has happened once, "it will work in
   Production" is an inference, not an observation.
2. **Close F1** — dedup deposits/withdrawals on `ReferenceId` (unique index +
   duplicate-as-success), the one reproduced money defect open this pass.
3. **Turn on market-maker exposure alerting** (#124) before the first customer-facing trade; the
   shop's book may legitimately sit deeply negative and nothing watches it.
4. **Decide the deployment-override story** for the shared config file (§10) so hosts can vary
   ports/connection strings without editing a file that also holds live credentials.
5. **Before scaling Orders.Api beyond one instance**, add a lease column to the outbox or
   document the single-instance constraint operationally (§9; the code already says it).
