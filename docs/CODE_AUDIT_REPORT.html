۱. خلاصه اجرایی

▾

TallaEgg یک پروتوتایپ کارکردی، بالغ در ساختار اما ناپخته در جزئیات حیاتی است. اسکلت معماری (میکروسرویس با تفکیک Api/Application/Core/Infrastructure و پایگاه‌داده‌ی مجزا به‌ازای هر سرویس) نشان‌دهنده‌ی دانش معماری خوب است، اما لایه‌ی مالی سیستم — که قلب یک صرافی است — فاقد تضمین اتمی بودن، کنترل همزمانی و امنیت است.

سه دسته مشکل، این پروژه را از تولید دور نگه می‌دارند:

  • یکپارچگی مالی: نبود Transaction روی عملیات چندمرحله‌ای کیف پول، نبود Optimistic Concurrency، و شرط رقابتی‌ای که در آن سفارش پیش از قفل موجودی تطبیق می‌شود — یعنی امکان خلق یا نابودی پول.
  • امنیت: کلید API و توکن ربات تلگرام hardcode و کامیت‌شده، اعتبارسنجی TLS کاملاً خاموش، CORS باز، و احراز هویت خاموش خارج از Production.
  • بدهی فنی: کد مرده‌ی فراوان، Endpointهای stub زنده (مثل MakeTradeAsync)، پوشه‌های پروژه‌ی تکراری، و ناسازگاری گسترده.

در وضعیت فعلی برای پول واقعی امن نیست. ساختار برای رشد آماده است، ولی لایه‌ی مالی و امنیتی باید پیش از تولید بازنویسی شوند.

۳. معماری ۶٫۵/۱۰

▾

وضعیت فعلی: یک Modular Monolith تقسیم‌شده به میکروسرویس. هر Bounded Context (User, Wallet, Order, Affiliate) چهار لایه و پایگاه‌داده‌ی جداگانه دارد (Database-per-Service) و ارتباط از طریق HTTP Client است. انتخابی درست و بالغ.

بحرانی نقض قاعده‌ی وابستگی Clean Architecture

پروژه‌ی Orders.Application (منطق دامنه) به TallaEgg.TelegramBot.Infrastructure و TallaEgg.Infrastructure وابسته است:

<!-- Orders.Application.csproj -->
<ProjectReference Include="..\..\..\TelegramBot\TallaEgg.TelegramBot.Infrastructure\..." />
<ProjectReference Include="..\..\TallaEgg\TallaEgg.Infrastructure\..." />

چرا مشکل است: لایه‌ی Application باید فقط به Abstraction وابسته باشد؛ اینجا OrderService کلاس concrete به نام UsersApiClient و WalletApiClient را از Infrastructure می‌گیرد.
ریسک: تست واحد غیرممکن، و تغییر Infrastructure دامنه را می‌شکند.
راهکار: اینترفیس‌ها را در Core/Application تعریف کنید و پیاده‌سازی را در Infrastructure نگه دارید (DIP). اولویت: بالا.

زیاد تراکنش توزیع‌شده مدیریت‌نشده

یک معامله = تغییر DB سرویس Order + فراخوانی HTTP به Wallet. اگر Wallet شکست بخورد، سفارش تطبیق‌خورده می‌ماند اما موجودی جابه‌جا نمی‌شود. هیچ Saga/Outbox/جبرانی نیست.
راهکار: الگوی Outbox + رویدادمحوری، یا حداقل Retry + Reconciliation.

متوسط «Shared Kernel» متورم

TallaEgg.Core همه‌چیز (DTO، Enum، Auth، Mapper، Constant، سرویس تلگرام) را در خود دارد و همه به آن وابسته‌اند → Coupling سراسری؛ تغییر یک Enum کل سیستم را Rebuild می‌کند.

۴. یافته‌های بحرانی 🔴 (Blocker تولید)

▾

C-1 کلید API به‌صورت hardcode در سورس

public class APIKeyConstant {
    public const string TallaEggApiKey = "WOz9RDFLfDVuOGWcG7FM1WSzaB8pXhKmxLQFv3Ex...";
}

تنها مکانیزم احراز هویت، همین کلید است؛ در Git کامیت شده و به‌عنوان اعتبارنامه‌ی کلاینت هم استفاده می‌شود. چون const است، قابل چرخش نیست.
راهکار: Secret Manager / Env / Key Vault؛ حذف از تاریخچه‌ی Git؛ چرخش فوری.

C-2 توکن تلگرام و Connection Stringها در کانفیگ کامیت‌شده

// config/appsettings.global.json
"TelegramBotToken": "8398757414:AAGBdRZteYIYYsITF4YY33Ad..."

توکن لو رفته = تصاحب کامل ربات. باید فوراً از BotFather باطل و بازتولید شود.

C-3 نبود Transaction روی عملیات مالی چندمرحله‌ای

WalletService.ApplyTradeAsync شش عملیات با SaveChangesAsync جداگانه انجام می‌دهد:

await UnlockBalanceAsync(buyer, quoteAsset, qty*price);   // Save 1
await DecreaseBalanceAsync(buyer, quoteAsset, qty*price); // Save 2
await UnlockBalanceAsync(seller, baseAsset, qty);         // Save 3
await DecreaseBalanceAsync(seller, baseAsset, qty);       // Save 4
await IncreaseBalanceForTradeAsync(buyer, base...);       // Save 5
await IncreaseBalanceForTradeAsync(seller, quote...);     // Save 6

ریسک: Crash بین مرحله‌ی ۳ و ۵ = پول از خریدار کم شده اما به فروشنده نرسیده → پول ناپدید می‌شود. هیچ Rollback ممکن نیست.
راهکار: کل عملیات در یک IDbContextTransaction یا یک SaveChanges واحد.

C-4 نبود کنترل همزمانی خوش‌بینانه (Optimistic Concurrency)

هیچ RowVersion روی WalletEntity یا Order نیست (تأییدشده). الگو همه‌جا Read→Modify→Save است. دو درخواست همزمان روی یک کیف پول = Lost Update = دو برابر خرج شدن.
راهکار: افزودن [Timestamp] byte[] RowVersion و مدیریت DbUpdateConcurrencyException با Retry.

C-5 شرط رقابتی: تطبیق سفارش پیش از قفل موجودی

در OrderService.CreateOrderAsync ترتیب معکوس است: سفارش ابتدا Confirm و به موتور تطبیق (که هر ۱ ثانیه هم مستقل اجرا می‌شود) فرستاده می‌شود و سپس موجودی قفل می‌شود:

order = await CreateOrderAsync(limitCommand); // داخلاً Confirm + ProcessOrderAsync
if(order != null) {
    await _walletApiClient.LockBalanceAsync(...); // قفل بعد از تطبیق!
}

ریسک: سفارش پیش از قفل وجوه تسویه می‌شود؛ سپس در ApplyTradeAsync موجودی‌ای Unlock می‌شود که هرگز Lock نشده → موجودی نادرست/منفی.
راهکار: ترتیب درست: اعتبارسنجی ← قفل موجودی ← ثبت و تأیید ← ارسال به موتور تطبیق.

C-6 ثبت اشتباه چرخه‌ی حیات موتور تطبیق

builder.Services.AddScoped<IMatchingEngine, MatchingEngineService>();
builder.Services.AddHostedService<MatchingEngineService>();

دو نمونه‌ی کاملاً جدا ساخته می‌شود. SemaphoreSlim در هر نمونه جداست و هیچ هماهنگی ایجاد نمی‌کند؛ نمونه‌ی HostedService سمافور خودش را در finally با Dispose از بین می‌برد. تضمینِ «یک چرخه در هر زمان» یک توهم است و Double-Match ممکن است.
راهکار: Singleton مشترک با IServiceScopeFactory یا قفل توزیع‌شده در محیط چنداینستنسی.

C-7 غیرفعال بودن کامل اعتبارسنجی TLS

handler.ServerCertificateCustomValidationCallback = (m, cert, chain, err) => true;

در ctor اول WalletApiClient بدون هیچ gate محیطی → حمله‌ی Man-in-the-Middle روی ترافیک مالی. باید فقط در Development پشت #if DEBUG باشد.

C-8 Endpoint زنده‌ای که هیچ کاری نمی‌کند

WalletService.MakeTradeAsync (متصل به POST /api/wallet/transaction/trade) تمام منطق را کامنت کرده و فقط return new WalletBallanceDTO(); خالی برمی‌گرداند → فراخواننده تصور می‌کند انتقال انجام شده.

C-9 CORS کاملاً باز روی همه‌ی سرویس‌ها

app.UseCors(b => b.AllowAnyOrigin().AllowAnyMethod().AllowAnyHeader());

راهکار: لیست سفید Originهای مجاز از کانفیگ.

۵. تزریق وابستگی ۵/۱۰

▾
  • 🔴 ثبت دوگانه‌ی MatchingEngineService (Scoped + HostedService) — بند C-6.
  • 🟠 ثبت دوگانه‌ی IWalletApiClient در Orders: یک‌بار Typed HttpClient و بلافاصله AddScoped<IWalletApiClient, WalletApiClient> که ثبت اول را بازنویسی و به سازنده‌ی مبهم می‌رسد.
  • 🟠 تزریق concrete به‌جای اینترفیس: OrderService مستقیماً UsersApiClient و UserService مستقیماً UserMapper می‌گیرد.
  • 🟡 استفاده‌ی گسترده از Service Locator (GetRequiredService) در موتور تطبیق.
  • ✅ استفاده‌ی درست از IServiceScopeFactory برای حل «Singleton به Scoped وابسته نشود» — با کامنت توضیحی.

۶. اصول SOLID ۴٫۵/۱۰

▾
اصلوضعیتشاهد
SRP❌OrderService.CreateOrderAsync اعتبارسنجی + فراخوانی Wallet + ساخت سفارش + قفل + ساخت پاسخ را یکجا انجام می‌دهد (God-Method).
OCP⚠️نرخ کارمزد hardcode در دو جا با مقادیر متناقض (0.000 vs 0.001/0.002).
LSP—سلسله‌مراتب وراثت کم؛ نقض خاصی مشاهده نشد.

DIP❌نقض جدی — Application به concrete Infrastructure وابسته است.

۷. مدیریت خطا ۴/۱۰

▾
  • 🟠 نبود Middleware سراسری خطا (بدون UseExceptionHandler/ProblemDetails) — به‌جای آن ۹۸ بلوک catch (Exception ex) پراکنده.
  • 🟠 بلعیدن استثنا: در بسیاری Endpointها ex استفاده نمی‌شود و ۵۰۰ عمومی بدون لاگ برمی‌گردد → خطاها در Production ناپدید می‌شوند.
  • 🟠 قالب پاسخ ناسازگار: گاهی ApiResponse<T>، گاهی شیء ناشناس، گاهی مقدار خام.
  • 🟡 نشت اطلاعات: ApiResponse.Fail(ex.Message) پیام استثنای داخلی را به کاربر برمی‌گرداند.
  • 🟡 CancelAllActiveOrders با catch { continue; } خالی و «TODO logging» استثنا را می‌بلعد.

۸. لاگ‌نویسی ۴/۱۰

▾
  • 🟠 Placeholderهای بدون آرگومان در WalletApiClient: LogInformation("... {Amount} {Asset} for user {UserId}") بدون هیچ آرگومان → لاگ بی‌فایده و ساختار شکسته.
  • 🟠 آمیختن ILogger<T> و Serilog.Log استاتیک در OrderService.
  • 🟠 سریال‌سازی کل لیست سفارش‌ها با JsonConvert.SerializeObject در هر درخواستِ GetBestBidAskAsync → حجم لاگ و CPU بالا.
  • 🟠 TelegramLoggerService استثناها را در catch { } خالی می‌بلعد و به SendExceptions.txt در cwd می‌نویسد.
  • 🟡 اموجی در پیام‌های لاگ (🚀💥🛑) — در Sink/grep مشکل‌ساز.
  • ✅ Serilog با Rolling File و فیلتر سطح لاگ EF Core — پایه‌ی خوب.

  • افزودن RowVersion (C-4)؛ Transaction واحد روی ApplyTradeAsync (C-3).
  • اصلاح ترتیب «قفل پیش از تطبیق» (C-5)؛ اصلاح DI موتور تطبیق (C-6).
  • Idempotency بر اساس ReferenceId؛ حذف/تکمیل متدهای stub مالی (C-8).

🟠 فاز ۲ — معماری و کیفیت

  • اینترفیس‌گذاری کلاینت‌ها و حذف وابستگی Application به Infrastructure.
  • Middleware سراسری خطا با ProblemDetails؛ یکدست‌سازی قالب پاسخ و کدهای HTTP.
  • AsNoTracking و انتقال فیلترها به دیتابیس.

🟢 فاز ۳ — بلوغ تولیدی

  • FluentValidation، Value Objectها، Outbox/Saga.
  • کشینگ قیمت، CancellationToken، تست واحد لایه‌ی مالی، خروج Migration از Startup.
