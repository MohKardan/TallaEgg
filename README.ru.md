## Обзор

TallaEgg позволяет ювелирному магазину торговать золотом со своими клиентами через Telegram.

Магазин публикует двустороннюю котировку — цену, по которой он покупает, и цену, по которой продаёт, вводимые одной парой `71000000-80000000`. Одобренные клиенты видят эту котировку и заключают сделку по любой из её сторон. Контрагентом в каждой сделке выступает магазин; клиенты никогда не торгуют друг с другом.

Новый пользователь, запустивший бота, регистрируется, делится номером телефона и ждёт одобрения магазина. До этого у него нет никакого доступа. Для торговли ему нужен либо баланс, либо кредит, который магазин выдаёт вручную — кредит является пределом, до которого его золотой баланс может уходить в минус, поэтому десять граммов кредита позволяют клиенту продать десять граммов, которых у него ещё нет.

Одобренные клиенты могут торговать по опубликованной котировке, просматривать историю своих сделок и производить физические расчёты с магазином.

## Ключевые возможности

- **Дилерская модель котировок (Dealer)** — магазин публикует котировку; ордера создаются только в момент исполнения и сразу же расходуются, поэтому никакое обеспечение не остаётся заблокированным в книге заявок.
- Атомарные расчёты по сделкам через транзакционный outbox, идемпотентные по идентификатору сделки, с блокировкой обеспечения до того, как ордер станет доступен для сопоставления.
- Домен кошельков: пополнения, выводы, блокировка баланса, кредит в золоте, история транзакций и автоматическое создание кошельков по умолчанию.
- RESTful minimal API для пользователей, кошельков и ордеров, возвращающие единую обёртку `ApiResponse<T>`.
- Telegram-бот, который использует API платформы и обслуживает весь опыт клиента и оператора через long polling.
- Централизованная конфигурация (`config/appsettings.global.json`), логирование через Serilog и типизированные HTTP-клиенты во всех сервисах.
- Движок сопоставления для одноранговых книг заявок по-прежнему есть в коде, но **не работает для символов Dealer** — см. [Торговая модель](#trading-model).

## Торговая модель

Платформа поддерживает два режима рынка для каждого символа, задаваемые в конфигурации:

| Режим | Поведение |
| --- | --- |
| **`Dealer`** (текущий) | Магазин публикует котировку. Когда клиент её принимает, оба ордера создаются и сопоставляются в одной операции. Фоновый движок сопоставления **полностью пропускает эти символы** — иначе он добрался бы до той же пары ордеров, которую уже сопоставляет исполнение, и из одной сделки получилось бы две. |
| `OrderBook` | Классическое сопоставление maker/taker через фоновый движок. Сегодня в продакшене не используется. |

`MAUA/IRT` (золото / томан), `SEKE_BAHAR/IRT` (монета «Бахар Азади» / томан) и `BTC/IRT` (биткоин / томан) работают в режиме `Dealer`. Контрагентом исполнения является тот, кто опубликовал котировку, поэтому указывать магазин в конфигурации не нужно.

### Добавление торгового символа

Возможность торговать символом определяется двумя независимыми вещами, которые намеренно разделены:

| Что | Где хранится | Как меняется |
| --- | --- | --- |
| **Метаданные** — точность дробной части, минимальное/максимальное количество, отображаемое название на персидском, какой инструмент nerkh.io/brsapi.ir задаёт цену | `Symbols:{Base}/{Quote}` в `appsettings.global.json` (см. уже имеющийся там блок для трёх символов выше) | Отредактируйте файл, перезапустите затронутые сервисы. Без изменения кода и без пересборки. |
| **Активен или нет** — отображается в выборе символа у клиента, участвует в автокотировании, доступен для ручной котировки | Одна строка в базе данных на символ (`SymbolSettings`, рядом с `AutoQuoteSettings`) | Команда бота, сразу и без перезапуска: `نماد فعال [سکه\|بیت]` / `نماد غیرفعال [...]`. Без ключевого слова подразумевается MAUA/IRT. |

Символу стандартного вида — номинированному в томанах и оцениваемому через nerkh.io и/или brsapi.ir так же, как уже оцениваются золото, монета и биткоин, — нужен **только блок конфигурации**, а затем администратор, который его включит. `TallaEgg.Core.CurrenciesConstant` содержит три символа выше в качестве скомпилированных значений по умолчанию (поэтому набору тестов и свежему клону репозитория файл конфигурации вообще не нужен); блок конфигурации для *нового* ключа добавляет к ним четвёртую запись, а блок для *существующего* ключа переопределяет только те поля, которые в нём заданы.

`Matching:MarketModes` (см. выше) — это ещё одна отдельная настройка: она выбирает между `Dealer` и `OrderBook` и по-прежнему требует собственной записи для каждого символа.

Символу, цена которого берётся из источника, не охватываемого ни nerkh.io, ни brsapi.ir, по-прежнему нужен новый класс, реализующий `Orders.Core.IReferencePriceProvider`, — это единственная часть, которая неизбежно требует кода, поскольку речь идёт о новой внешней интеграции, а не о новом определении символа.

## Технологический стек

- .NET 9.0 с C# 12, minimal API и фоновыми службами.
- Entity Framework Core 9 с провайдером SQL Server.
- Serilog для структурированного логирования в консоль и ротируемые файлы.
- Telegram.Bot через long polling — **входящие порты не требуются**.
- Типизированные обёртки `HttpClient` для вызовов между сервисами.

## Требования

- .NET SDK 9.0.
- **SQL Server Express**, доступный с хоста (именованный экземпляр `SQLEXPRESS`, проверка подлинности Windows). Не LocalDB — LocalDB является пользовательским экземпляром, запускаемым по требованию, которого нет на сервере, и именно это ломало развёртывание до [#68](https://github.com/MohKardan/TallaEgg/issues/68). Express — тот же движок, на котором работает реальное (одномашинное) развёртывание, только установленный локально.
- Токен Telegram-бота от [@BotFather](https://t.me/BotFather).
- Ваш собственный числовой идентификатор пользователя Telegram (спросите у [@userinfobot](https://t.me/userinfobot)) — именно он делает вас оператором магазина на новой базе данных.

## Конфигурация

Каждый сервис загружает `config/appsettings.global.json`, а затем разворачивает раздел под `Services:`, совпадающий с именем его сборки. Отдельного `appsettings.json` для каждого сервиса, который нужно было бы поддерживать, нет.

> ⚠️ **Старые токены бота и старый общий API-ключ всё ещё можно прочитать в истории git этого репозитория**, потому что этот файл раньше отслеживался. В отслеживаемых исходных файлах токенов больше нет. **Считайте всё, что найдено в истории, скомпрометированным, и не полагайтесь на слова документа о том, что оно заменено**: проверьте и, если оно всё ещё работает, отзовите токен через BotFather (или замените ключ). История намеренно **не** переписывается — средство здесь замена секретов; это решение и его обоснование описаны в [#105](https://github.com/MohKardan/TallaEgg/issues/105). Сам файл конфигурации теперь игнорируется git; не добавляйте ни его, ни какие-либо новые секреты обратно в систему контроля версий.

### Важные настройки

| Настройка | Почему это важно |
| --- | --- |
| `BotSettings:OwnerTelegramIds` | Единственное, что позволяет кому-либо войти в систему на пустой базе данных. Указанный здесь владелец при регистрации автоматически одобряется и получает роль `Admin`. Укажите здесь **свой собственный** идентификатор Telegram. |
| `BotSettings:DefaultReferralCode` | Должно быть `admin` — это код строки администратора, которую создаёт `Users.Api`. Регистрация отклоняет любой код, не принадлежащий ни одному пользователю, поэтому несовпадение здесь означает, что **зарегистрироваться не сможет никто**. |
| `Matching:MarketModes` | Если ни один символ не установлен в `"Dealer"` (например, `"MAUA/IRT": "Dealer"`), используется `OrderBook`, и любое исполнение котировки по этому символу отклоняется. |
| `TelegramBotToken` | Обычно читается из этого файла, и без него бот отказывается запускаться. Резервного варианта `TELEGRAM_BOT_TOKEN` нет — это имя не проверяется. Тем не менее ключ можно переопределить для отдельного процесса, поскольку цепочка конфигурации бота заканчивается переменными окружения, а затем командной строкой (#181), так что и `TelegramBotToken=...` в окружении, и `--TelegramBotToken=...` в командной строке имеют приоритет над файлом. |

### Порты и адреса привязки

Каждая запись `Urls` выше — намеренно обычный HTTP на loopback-интерфейсе (`localhost`) — см. [#69](https://github.com/MohKardan/TallaEgg/issues/69):

- Бот обращается к Telegram через **long polling**; соединение устанавливает он сам, Telegram никогда не подключается к нему.
- Четыре настоящих API вызываются только ботом, на том же хосте.
- Поэтому **никакой входящий порт открывать не нужно**, как не нужен и адрес привязки HTTPS — запись `https://localhost:...` требует сертификата разработки, которого на сервере не будет, а между открытым в интернет портом и базой данных оставался бы только упомянутый выше общий API-ключ. Привязка к loopback здесь и есть реальная мера безопасности, а не заглушка, которую нужно заменить.

| Сервис | Порт | Назначение |
| --- | --- | --- |
| Users.Api | 5136 | Регистрация, роли, создание кошельков |
| Wallet.Api | 60933 | Балансы, расчёты |
| Orders.Api | 5140 | Котировки, сделки, сопоставление |
| Affiliate.Api | 60812 | Не развёртывается — см. [Настройка базы данных](#database-setup) |
| TallaEgg.TelegramBot.Infrastructure | 57546 | Настроен, но его никто не слушает — бот является простым универсальным хостом без веб-сервера и обращается к Telegram через long polling |
| TallaEgg.Api | 5135 | Не развёртывается — устаревший, никем не вызывается |

На реальном сервере убедитесь, что ни один из этих портов не отображается в `netstat`/`ss` на публичном интерфейсе — только на `127.0.0.1`.

### Общий API-ключ

Wallet.Api, Users.Api, Orders.Api и Affiliate.Api аутентифицируют вызовы между сервисами общим ключом, передаваемым в заголовке `X-API-Key` (`TallaEgg.Core.APIKeyConstant`). Он читается из переменной окружения `TALLAEGG_API_KEY`, а не из какого-либо отслеживаемого файла.

- **Разработка**: ни один из четырёх сервисов его не требует — аутентификация по API-ключу подключается только при `ASPNETCORE_ENVIRONMENT=Production`. Локально оставьте переменную незаданной.
- **Продакшен**: задайте `TALLAEGG_API_KEY` перед запуском любого сервиса; если она отсутствует, каждый сервис выбрасывает исключение при запуске — ещё до привязки своего порта.

> **На сервере `ASPNETCORE_ENVIRONMENT` нужно задавать явно.** Локально `dotnet run` всегда сообщает `Development` из-за `launchSettings.json` — этот файл не используется опубликованным развёртыванием, поэтому вне `dotnet run` сервер по умолчанию работает в `Production`, как только переменная задана (или оставлена неявной). До [#69](https://github.com/MohKardan/TallaEgg/issues/69) путь кода `Production` — аутентификация по API-ключу, без исключения для перенаправления на Swagger — ни разу реально не выполнялся.

<a id="database-setup"></a>
## Настройка базы данных

Каждый API вызывает `Database.MigrateAsync()` при запуске, поэтому схема создаётся при первом запуске. Для Users, Wallet и Orders ручные действия не нужны.

Чтобы применить миграции заранее:

```
dotnet restore
dotnet tool install --global dotnet-ef
dotnet ef database update --project src/User/Users.Api/Users.Api.csproj
dotnet ef database update --project src/Wallet/Wallet.Api/Wallet.Api.csproj
dotnet ef database update --project src/Order/Orders.Api/Orders.Api.csproj
```

`Users.Api` создаёт одну строку администратора (`5564f136-b9fb-4719-b4dc-b0833fa24761`), единственное назначение которой — владеть начальным пригласительным кодом. У неё нет идентификатора Telegram, и войти под ней нельзя.

> **У Affiliate нет миграций.** `Affiliate.Api` вызывает `MigrateAsync()`, но не содержит ни одного файла миграции, поэтому запускается без ошибок, а затем каждый запрос завершается ошибкой `Invalid object name 'Invitations'`. Сейчас его никто не вызывает — единственный вызов приглашения в боте закомментирован, — поэтому его можно не включать в развёртывание.

## Первый запуск

На пустой базе данных это вся настройка. Не нужно выполнять SQL и копировать идентификаторы между файлами.

1. Укажите свой идентификатор Telegram в `BotSettings:OwnerTelegramIds` и запустите сервисы.
2. Отправьте боту `/start`, затем поделитесь номером телефона, когда будет предложено.
   → Вы автоматически одобрены и получаете роль `Admin`.
3. Опубликуйте котировку, отправив цены покупки и продажи одной парой, например `79000000-79500000`.
4. Попросите клиента отправить `/start` и поделиться номером, затем одобрите его: `ت <его телефон>`.
5. Выдайте ему кредит: `ش <его телефон> 10 طلا`.
6. Теперь он может торговать по опубликованной котировке.

### Команды оператора

Цены указываются за мискаль (mesghal); количество золота — в граммах. Числа можно вводить персидскими или латинскими цифрами.

| Команда | Действие |
| --- | --- |
| `<buy>-<sell>` | Опубликовать котировку, например `79000000-79500000` |
| `ت <phone>` | Одобрить аккаунт |
| `ر <phone>` | Отклонить аккаунт |
| `ن <phone> <role>` | Изменить роль — `کاربر عادی`, `حسابدار`, `مدیر`, `مدیر ارشد` |
| `ش <phone> <amount> <asset>` | Зачислить на аккаунт, например `ش 09121234567 500000 تومان` |
| `د <phone> <amount> <asset>` | Списать с аккаунта |
| `م <phone>` | Показать балансы |
| `س <phone>` | Показать открытые ордера пользователя |
| `ک [search]` | Список пользователей |

## Локальный запуск

Соберите один раз, затем запустите каждый сервис в отдельном терминале. Сборка при запущенных сервисах завершается ошибкой из-за заблокированных DLL.

```
dotnet build TallaEgg.sln

dotnet run --no-build --project src/User/Users.Api/Users.Api.csproj
dotnet run --no-build --project src/Wallet/Wallet.Api/Wallet.Api.csproj
dotnet run --no-build --project src/Order/Orders.Api/Orders.Api.csproj
dotnet run --no-build --project TelegramBot/TallaEgg.TelegramBot.Infrastructure/TallaEgg.TelegramBot.Infrastructure.csproj
```

`Affiliate.Api` не нужен (см. выше). `src/TallaEgg/TallaEgg.Api` — устаревший API оркестрации, который никто не вызывает.

Swagger UI доступен по адресу `/api-docs` в Users, Wallet и Orders — например, `http://localhost:5136/api-docs`. Он подключается **только при `ASPNETCORE_ENVIRONMENT=Development`**, поэтому на развёрнутом сервере его нет; `dotnet run` задаёт это значение из `launchSettings.json`, так что локально он доступен по умолчанию. Бот вообще не предоставляет HTTP-эндпоинтов.

<a id="production-deployment"></a>
## Развёртывание в продакшене

На сервере четыре развёртываемых сервиса (не Affiliate.Api и не TallaEgg.Api — см. выше) работают как нативные службы Windows, а не по терминалу на процесс, поэтому они автоматически перезапускаются после сбоя или перезагрузки. Разовая настройка и скрипты установки из `scripts/windows-services/` описаны в [`docs/operations/WINDOWS_DEPLOYMENT.md`](docs/operations/WINDOWS_DEPLOYMENT.md) — issue #70.

## Сервисы в кратком изложении

- **Users.Api** — регистрация по пригласительным кодам, обновление телефона, управление ролями и статусами, создание кошельков по умолчанию, поиск по идентификатору Telegram, телефону или роли.
- **Wallet.Api** — балансы, пополнения, выводы, блокировка/разблокировка, атомарные расчёты по сделкам, история транзакций.
- **Orders.Api** — публикация и история котировок, исполнение котировок, история сделок, лучшие цены покупки/продажи и движок сопоставления (неактивный для символов Dealer).
- **Telegram-бот** — хост с long polling, типизированные API-клиенты, уведомления о сделках и описанные выше команды оператора.
- **Affiliate.Api** — пригласительные коды. Присутствует, но не работает; см. примечание в разделе «Настройка базы данных».

<a id="testing"></a>
## Тестирование

```
dotnet test TallaEgg.sln
```

**`tests/TallaEgg.AllServices.Tests` — единственный тестовый проект в решении**; он содержит набор тестов для всей платформы — кошельки, ордера, сопоставление, исполнение котировок, обработчики бота и форматирование. Новые тесты размещаются здесь, независимо от того, какой сервис они покрывают.

Название намеренно явное. До #117 этот проект назывался `src/Wallet/Wallet.Tests`, хотя к тому времени только восемь из его пятидесяти шести файлов относились к кошельку — это вводило в заблуждение настолько, что аудит сообщил об отсутствии тестов у бота, потому что его тесты лежали не в папке с названием бота.

CI запускает `dotnet test TallaEgg.sln`, а не указывает этот проект по пути, поэтому будущий тестовый проект подхватывается простым добавлением в решение, и больше ничего помнить не нужно.

## Логирование

Каждый сервис пишет в консоль и в ротируемый файл в каталоге `logs/` **рядом со своим исполняемым файлом**, а не в каталоге, из которого он был запущен.

При `dotnet run` это каталог вывода сборки — `src/Order/Orders.Api/bin/Debug/net9.0/logs/orders-api-<date>.log`. На развёрнутой машине это папка публикации — `C:\TallaEgg\publish\Orders.Api\logs\orders-api-<date>.log`. Для случая развёртывания, который до [#211](https://github.com/MohKardan/TallaEgg/issues/211) писал в `C:\Windows\System32\logs\`, см. [`docs/operations/WINDOWS_DEPLOYMENT.md`](docs/operations/WINDOWS_DEPLOYMENT.md).

## Развёртывание

Благодаря long polling боту **не нужны входящие порты**. Работа KR1 по развёртыванию ([#68](https://github.com/MohKardan/TallaEgg/issues/68) база данных, [#69](https://github.com/MohKardan/TallaEgg/issues/69) продакшен-адреса, [#70](https://github.com/MohKardan/TallaEgg/issues/70) надзор за процессами и [#71](https://github.com/MohKardan/TallaEgg/issues/71) CI) завершена — фактические шаги см. в разделе [Развёртывание в продакшене](#production-deployment) выше и в [`docs/operations/WINDOWS_DEPLOYMENT.md`](docs/operations/WINDOWS_DEPLOYMENT.md). Режим `Production` запускался и проверялся локально на SQL Server Express, а не только Development, — прежнее примечание здесь о том, что он ни разу не выполнялся, больше не соответствует действительности.

Для публикации и установки сервисов используйте `scripts/windows-services/` — теперь это единственный инструмент публикации в репозитории. Более старый `publish-all.ps1` в корне и папка `publishes/` появились до #69/#70 и были удалены: они публиковали пять сервисов вместо четырёх (включая два, которые #69 решил не развёртывать), всё ещё ссылались на адреса привязки HTTPS, удалённые в #69, и предполагали ручной запуск через `dotnet *.dll` вместо службы под надзором.
